# QA audit: ketch (2026-10-01)

Find-only audit. No code was changed. The reproductions below were run as temporary
unit tests that were then removed; this document is the only committed file.

## Scope

- Repository: `pyrlyn/ketch`, branch `main` at `22e4bb3`
  ("fix!: refuse an ambiguous bin glob instead of taking directory order (#202)").
- Covered: `crates/ketch-core` (download, checksum verification, archive extraction,
  local-package hashing, package-spec parsing, version ordering), the CLI front end in
  `src/`, and the `install.sh` bootstrap script.
- Not covered: the macOS desktop app (`desktop/`), the site, release workflows, Windows
  and Linux runtime behaviour (CI-only on this host).
- Focus: wrong implementations, missing input and argument checks, missing error
  handling, and anything that reliably errors or breaks. Security issues are described
  only; nothing was exploited.

## Test plan

1. Run the checks CI runs on macOS: `cargo fmt --check`, `cargo clippy -D warnings`,
   `cargo nextest run --workspace --all-targets` with and without `--features tui`.
2. Read the trust-critical paths: `install::verify_checksum`, `source::github`
   checksum discovery and parsing, `extract::archive` (detection, tar/zip unpack,
   permissions), `source::local::sha256_tree`, `model::PackageSpec`/`Version`, `install.sh`.
3. For each suspected defect, write the smallest unit test or CLI call that shows it,
   record the output, then remove the test.
4. Run edge-case CLI input against a throwaway root (`KETCH_ROOT=/tmp/...`).

### 1. A failed checksum-file fetch is treated as "no checksum published"

- **Severity:** medium
- **Impact:** If GitHub returns a 403 or 5xx, or the network drops while ketch fetches a
  release's `.sha256` sidecar or `SHA256SUMS`, the asset installs **unverified**. It is
  recorded as trust-on-first-use (`checksum_verified: false`) and only a debug line is
  logged. Anyone who can make the checksum request fail (rate limiting, a flaky proxy,
  an on-path attacker who can block one URL but not forge TLS) turns off verification
  without the user knowing. With `require_checksums`, the user gets the misleading
  `ChecksumMissing` error instead of the real network error. `GitHubSource::checksums`
  deliberately returns that error ("a dead network or a 403 ... must not be reported as
  'no published checksum'"), and the caller then throws it away.
- **Environment:** any OS. Assets with no API `digest` (older releases, or other forges
  through plugins).
- **Steps to reproduce:**
  1. Implement a `Source` whose `checksums()` returns
     `Err("could not fetch checksum file tool.tar.gz.sha256: HTTP 403")`.
  2. Call `install::verify_checksum(&src, "o/r", &release, &asset, &hash, false, &Report::silent())`
     on an asset with `digest: None`.
  3. Repeat with `require = true`.
- **Expected:** both calls return the fetch error.
- **Actual:** `require=false -> Ok(false)`, and `require=true -> Err(ChecksumMissing("tool.tar.gz"))`.
- **Evidence:** temporary test `install::qa_repro::qa_checksum_fetch_error_is_swallowed_into_tofu`,
  output above.
- **Suggested fix:** in `verify_checksum`, pass on `Err` from `source.checksums()`
  (`?`) instead of `unwrap_or_else(.. Default::default())`. Or turn it into a distinct
  "could not verify" error that never falls through to the TOFU branch.
- **Missing check/error handling:** `crates/ketch-core/src/install.rs:1380-1386`
  (`verify_checksum`, the `unwrap_or_else` on `source.checksums`). Also affects
  `crates/ketch-core/src/self_update.rs:522` (same call, misleading error).

### 2. Archive permissions applied verbatim (setuid, world-writable)

- **Severity:** medium
- **Impact:** Release archives are untrusted client data, but tar members keep their
  exact mode (`set_preserve_permissions(true)`), and zip members get
  `mode & 0o7777`. A member marked `0o4777` is written as setuid and world-writable
  in the store, and that file is then linked onto `PATH`. On a multi-user machine any
  other local user can overwrite a binary the victim runs. Setuid and setgid bits on
  user-owned files are also kept for no reason. The process umask is bypassed because
  `set_permissions` ignores it.
- **Environment:** macOS and Linux (Unix modes only).
- **Steps to reproduce:**
  1. Build a tar with one regular member `tool`, mode `0o4777`.
  2. Run `extract::archive::unpack_tar(&archive, dest)`.
  3. `stat` the result.
- **Expected:** the mode is masked to at most `0o755` (or `0o644` plus the exec bits),
  with no setuid/setgid/sticky bits and no group or world write.
- **Actual:** `mode on disk: 4777`.
- **Evidence:** temporary test `extract::archive::qa_repro::qa_archive_modes_preserved_world_writable_and_setuid`.
- **Suggested fix:** mask modes with `& 0o755` (keep the exec bits, drop
  `0o7022`) for tar and zip members alike. For tar, either use
  `set_preserve_permissions(false)` and apply the masked mode after `unpack`, or call
  `set_unix_mode(out, header_mode & 0o755)` after each regular-file unpack.
- **Missing check:** `crates/ketch-core/src/extract/archive.rs:276`
  (`set_preserve_permissions(true)`), `:331` (tar regular-file unpack),
  `:484` (`set_unix_mode(&out, mode & 0o7777)` for zip).

### 3. Local-package tree hash is ambiguous (collisions; symlinks and modes ignored)

- **Severity:** medium
- **Impact:** `sha256_tree` is what `ketch.lock` pins a local or `.app` package to
  (`install.rs:324-327`, `check_locked`). It hashes `rel_path \0 bytes` for each file
  with no length framing. So two different trees can produce the same digest, and a
  lockfile check passes for content that differs from what was locked. It also skips
  symlinks (only `is_file()` is hashed) and ignores the exec bit, so re-pointing a
  symlink inside an `.app` bundle or dropping `+x` leaves the hash unchanged.
- **Environment:** any OS. `ketch install --path` / `local:` plus `ketch sync`/`lock check`.
- **Steps to reproduce:**
  1. Tree A: file `a` = `X`, file `b` = `Y`.
  2. Tree B: a single file `a` = `Xb\0Y`.
  3. Compute `source::local::sha256_tree` on both.
- **Expected:** different digests.
- **Actual:** both are
  `fcdcf93cd1ef536fba84fd05e3ef0fa57922c0577e69cb9214110e8ca306c889`.
- **Evidence:** temporary test `source::local::qa_repro::qa_tree_hash_is_ambiguous`.
- **Suggested fix:** frame every record, e.g. hash
  `kind || len(path) || path || mode || len(content) || content`, with symlinks
  recorded as `kind=link` plus the target. This changes recorded hashes, so it needs
  a lockfile-format note or a version bump (a product decision).
- **Missing check:** `crates/ketch-core/src/source/local.rs:410-429`.

### 4. A lone `.xz` / `.bz2` binary is detected as a tarball and cannot install

- **Severity:** medium
- **Impact:** Releases that ship one compressed executable (`tool-linux-amd64.xz`,
  `tool.bz2`; common for Go and Rust tools) always fail to install with
  `failed to read entire block`. Gzip has both a `TarGz` and a `GzFile` extractor
  that check the inner tar header. Xz and bz2 match on magic bytes only and go
  straight to `unpack_tar`. The bare-binary fallback is never reached.
- **Environment:** any OS.
- **Steps to reproduce:**
  1. xz-compress a small binary into `tool-linux-amd64.xz`.
  2. `TarXzExtractor.detect(path, head)` returns `true`.
  3. `TarXzExtractor.extract(path, dest)`.
- **Expected:** one decompressed executable in `dest`, as the `.gz` case gives.
- **Actual:** `Err(Io { .., "failed to read entire block" })`, and `dest` stays empty.
- **Evidence:** temporary test `extract::archive::qa_repro::qa_lone_xz_file_is_treated_as_tarball`.
  The bz2 path has the same structure (`detect` checks `BZh` only) but was not
  run, so it is suspected.
- **Suggested fix:** make `TarXz`/`TarBz2` detection peek at the decompressed head
  with `looks_like_tar`, as `gzip_inner_head` does. Add `XzFileExtractor` and
  `Bz2FileExtractor` that mirror `GzFileExtractor`.
- **Missing check:** `crates/ketch-core/src/extract/archive.rs:393-395`
  (`TarXzExtractor::detect`), `:412-414` (`TarBz2Extractor::detect`).

### 5. Aggregate checksum lists collapse entries with the same basename

- **Severity:** low
- **Impact:** `parse_checksum_file` keeps only the file name
  (`rsplit('/')`) and `insert`s, so the last line wins. A `SHA256SUMS` that lists
  `linux/tool.tar.gz` and `darwin/tool.tar.gz` gives one hash for both. One
  platform then always fails with a false `ChecksumMismatch`, and the user cannot
  install a legitimate release.
- **Environment:** any OS.
- **Steps to reproduce:** call `parse_checksum_file` on
  `"111..  linux/tool.tar.gz\n222..  darwin/tool.tar.gz\n"`.
- **Expected:** both entries kept, or the ambiguity reported and the name treated as
  having no unique published checksum.
- **Actual:** `{"tool.tar.gz": "2222…"}`.
- **Evidence:** temporary test `source::github::qa_repro::qa_same_basename_in_aggregate_overwrites`.
- **Suggested fix:** detect a repeated basename with a different hash and drop that
  key (or mark it ambiguous) instead of overwriting.
- **Missing check:** `crates/ketch-core/src/source/github.rs:306-308`.

### 6. A multi-line `.sha256` sidecar uses the alphabetically first hash, not the asset's

- **Severity:** low
- **Impact:** For a sidecar `tool.tar.gz.sha256`, ketch parses it as a checksum list and
  takes `into_values().next()`, which is the alphabetically first key of a
  `BTreeMap`, not the entry named `tool.tar.gz`. A sidecar that lists more than one
  file (some release tools write the whole list into every sidecar) produces a false
  checksum mismatch.
- **Environment:** any OS.
- **Steps to reproduce:** sidecar body
  `"111..  tool.tar.gz\n222..  a-tool.tar.gz\n"` for target `tool.tar.gz`.
- **Expected:** `111…`.
- **Actual:** `222…` is picked.
- **Evidence:** temporary test `source::github::qa_repro::qa_sidecar_with_several_lines_takes_alphabetical_first`.
- **Suggested fix:** look up `parsed.get(target)` first. Fall back to the single value
  only when the sidecar has exactly one entry.
- **Missing check:** `crates/ketch-core/src/source/github.rs:423-427`.

### 7. An empty version after `@` is not rejected

- **Severity:** low
- **Impact:** `ketch install owner/repo@` (a typo, or an empty shell variable
  `owner/repo@$VER`) is parsed as `VersionSpec::Exact("")`. It spends API requests
  (`/releases/tags/`, then a full listing walk) and ends with the misleading
  `no release found for `ripgrep``, when it should be an input error.
- **Environment:** any OS, network available.
- **Steps to reproduce:**
  1. `KETCH_ROOT=$(mktemp -d) ketch why BurntSushi/ripgrep@`
- **Expected:** an immediate error like ``empty version after `@` ``.
- **Actual:** `candidate (none)` then `error no release found for `ripgrep``.
- **Evidence:** CLI output from the debug build at `22e4bb3`.
- **Suggested fix:** in `PackageSpec::parse`, treat a trailing `@` (empty or
  whitespace-only version) as an error, or return `Result` and report it at the CLI.
- **Missing check:** `crates/ketch-core/src/model.rs:334-341`.

### 8. `install.sh` looks up the expected hash with an unanchored regex `grep`

- **Severity:** low (suspected; the current v0.9.0 `SHA256SUMS` is fine)
- **Impact:** `grep "${TARBALL_NAME}" SHA256SUMS` matches substrings and treats `.` as
  any character. If `SHA256SUMS` ever lists a second name that contains the tarball
  name (`ketch-…tar.gz.sig`, `.sha256`, `-debug`…), `EXPECTED_HASH` holds two lines,
  never equals the real hash, and every bootstrap install fails with "Checksum
  verification failed!".
- **Environment:** macOS/Linux bootstrap.
- **Steps to reproduce:**
  1. Add a line `<hash>  ketch-aarch64-apple-darwin.tar.gz.sig` to a copy of `SHA256SUMS`.
  2. Run the lookup line from the script against it.
- **Expected:** exactly one hash.
- **Actual (by inspection):** two hashes joined by a newline.
- **Suggested fix:**
  `awk -v n="$TARBALL_NAME" '$2==n || $2=="*"n {print $1; exit}' SHA256SUMS`.
- **Missing check:** `install.sh:248`.

### 9. `Version`'s `PartialEq` disagrees with its `Ord`

- **Severity:** low (suspected)
- **Impact:** `Version` derives `PartialEq` over `raw` and `sem`, while `Ord` strips a
  leading `v` and compares as equal. So `v1.0.0` and `1.0.0` give `cmp == Equal`
  but `!=` is true, which breaks the `Ord` contract. `install.rs:664`
  (`p.version != release.version`) can then run update hooks with
  `KETCH_PREVIOUS_VERSION` set to the same version. `retain` filters at
  `install.rs:1174` and `:1492` can keep duplicates.
- **Environment:** any OS.
- **Steps to reproduce:**
  `Version::parse("v1.0.0") == Version::parse("1.0.0")` is `false`, and
  `.cmp()` returns `Equal`.
- **Expected:** consistent equality.
- **Suggested fix:** implement `PartialEq`/`Eq` by hand as `self.cmp(other) == Equal`.
- **Missing check:** `crates/ketch-core/src/model.rs:376` (derive).

### 10. `--jobs` skips the 16-worker cap and silently accepts 0

- **Severity:** low
- **Impact:** `config.toml`/`KETCH_JOBS` values are clamped to `1..=16`
  (`config.rs:264`), but the `-j/--jobs` flag is not. `-j 500` on a large `upgrade` or
  `sync` opens hundreds of parallel GitHub requests and hits secondary rate limits.
  `-j 0` silently falls back to the default instead of failing.
- **Environment:** any OS.
- **Steps to reproduce:** `ketch upgrade -j 500` with many packages installed.
- **Expected:** a clap range check (`1..=16`) or the same clamp as the config.
- **Actual:** the value is used as given (bounded only by the package count).
- **Suggested fix:**
  `#[arg(value_parser = clap::value_parser!(usize).range(1..=16))]`, or `.min(16)`
  in `cmd::pkg::jobs`.
- **Missing check:** `src/cmd/pkg.rs:533-535`, `src/cli.rs:203,262,366,428`.
